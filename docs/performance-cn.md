# 性能对比与测量方法

> 本文为中文翻译，以英文版 [performance.md](./performance.md) 为准。

本项目的性能数据都记录在本文：各形态的测量值、**每个数字的来源**，以及
**哪些对比可信、哪些不可信**。部署文档只引用结论，不重复数据。

若只需确定应启用哪些开关，阅读第 1 节即可。

数据来自同一套 5 节点测试集群，采集时间 2026-09-15 ~ 2026-09-16；§6.1 那次会话的日期未记录。

## 1. 结论

| 结论 | 依据 |
|---|---|
| **性能提升来自 `bpf.hostLegacyRouting=false`**：Pod 流量 +16%~31% | §4 的 C→D，同会话、只改一个 Cilium 值（C 档时 kube-proxy 是否仍在运行未记录，见 §2）。C→D 之间锚点自身移动了 +10.9%，所以跨节点 PodIP 的 +16% 与这一移动同一量级；其余三格超过它（§4.2 规则 1） |
| **`kubeProxyReplacement=true` 本身在 Pod 发起的流量上没有本数据能分辨的收益** | §4 的 B 与 C 相差 −1.1% ~ +2.5%（B 相对 C），但两者来自不同会话，这只是低于 §4.2 分辨率的跨会话观察，不是测得差值为零。它的价值是充当上一条的**生效前提**，以及接管 NodePort 与宿主自身发起的 Service 流量 |
| **把默认档的两项关掉，串接一致地亏损**：比完全不串接最多慢约 10%。没有哪一格单独越过 §4.2 约 11% 的门槛；支撑它的是同一会话内四格同号 | §5。只有 host-routing 省掉宿主协议栈中对应的那段处理，tc/tcx 程序的开销才能补回 |
| **串接是否拖慢 hostNetwork 流量尚未确立** | §5。以 A 的锚点为基准，§4.1 中 B 为 −8.0%、D 为 −10.4%；主表中 D 为 +7.0%。同一对 D/A 在两次会话之间相差 17 个百分点，连方向都没有复现 |
| **delegated 模式（Cilium 创建 netkit 设备）相对默认档的增量低于测量分辨率** | §6。这是分辨率不足，不是差值为零，原因与条件见 §7 |

因此，使用 [deploy-cilium-chained-cn.md](deploy-cilium-chained-cn.md) 的**默认档**即可
（形态 D）：这两项本来就是该文档的默认值，不需要任何额外的代码路径，也不需要 delegated 模式。

| 代号 | 形态 |
|---|---|
| **A** | 仅本插件，不安装 Cilium（veth + per-ENI 策略路由，Service 由 kube-proxy 转发） |
| **B** | 串接，但把默认档的两项都关掉：`kubeProxyReplacement` 未开，`bpf.hostLegacyRouting` 未设（等价于 `true`；见部署文档 §4.2 表中 `kubeProxyReplacement` 与 `bpf.hostLegacyRouting` 两行） |
| **C** | 串接 + `kubeProxyReplacement=true`，但 `bpf.hostLegacyRouting=true`。kube-proxy 是否仍在运行未记录 |
| **D** | **串接模式的默认档**：`kubeProxyReplacement=true` + `bpf.hostLegacyRouting=false`，kube-proxy 已摘除 |
| **E** | delegated 模式：`cni.mode=delegated` + `bpf.datapathMode=netkit`，其余同 D（见 [deploy-cilium-netkit-cn.md](deploy-cilium-netkit-cn.md)） |

## 3. 测量方法

```bash
netperf -H <目标> -p 12865 -t TCP_RR -l 10 -- -r 1,1 -P ,12866
```

- **主指标是 TCP_RR（请求-响应速率）**，不是吞吐。延迟/pps 对数据面的每包开销最敏感，
  而吞吐在 25 Gbps 链路上容易受其他因素限制。
- **`-P ,12866` 不可省。** TCP_RR 的控制连接使用 12865，数据连接默认使用随机端口，经 ClusterIP
  时无法返回（结果为一排 0）。固定数据端口并将其加入 Service 后才能测通。
- 每格取 **3 次的中位数**（形态 E 的部分场景取到 10~17 次，见表下注）。
- **离散**（亦称「极差」）指同一格 n 次测量的 (最大值 − 最小值) / 中位数。引用时凡有记录都注明 n。
- 场景：同节点 Pod→PodIP、跨节点 Pod→PodIP、同节点 Pod→ClusterIP、跨节点 Pod→ClusterIP，
  外加 **hostNetwork Pod 跨节点**作为锚点（用法见 §4.2）。
- 环境：（集群 5 个节点中的）两台被测节点为 8 vCPU / 16 GiB 与 16 vCPU / 32 GiB，25 Gbps 网卡，双栈集群，
  Ubuntu 26.04（内核 7.0）、containerd 2.2、Kubernetes v1.34、Cilium v1.17.5，
  测前 load < 0.3。测试本身占用约 50 Mbps（链路的 0.2%）。同节点 Pod 对落在两台中的哪一台未记录。
- **绝对值随规格与内核变化**，本文的百分比只用于说明各形态之间的相对关系。

## 4. 结果

TCP_RR，单位 txn/s，中位数：

| 场景 | A 仅本插件 | B 串接·两项全关 | C 串接+KPR | **D 串接默认档** | E delegated+netkit |
|---|---|---|---|---|---|
| **hostNetwork 跨节点**（锚点） | 15493 | 15440 | 14959 | 16584 | 15156 |
| 同节点 Pod→PodIP | 27825 | 25503 | 25630 | **31274** | 32421 |
| 跨节点 Pod→PodIP | 14079 | 13386 | 13057 | **15163** | 15236 |
| 同节点 Pod→ClusterIP | 27216 | 24961 | 25247 | **33172** | 31902 |
| 跨节点 Pod→ClusterIP | 13458 | 13174 | 12945 | **16713** | 15460 |

> **采集会话**：A、C、D 三档同一会话连测；B 来自前一天；E 来自当晚。这决定了哪些列可以互比，
> 见 §4.2。
> **样本数**：A~D 每格 3 次；E 的同节点两行与跨节点 Pod→PodIP 为 10 次，hostNetwork 为 17 次，
> 跨节点 Pod→ClusterIP 为 3 次。

同会话的对比（C→D，只改 Cilium 的 `bpf.hostLegacyRouting` 一个值，其余 Cilium 值、节点、Pod 全部不变；
C 档时 kube-proxy 是否仍在运行未记录，所以摘除 kube-proxy 可能是第二处差异）：

| 场景 | C | D | 提升 |
|---|---|---|---|
| 同节点 Pod→PodIP | 25630 | 31274 | **+22%** |
| 跨节点 Pod→PodIP | 13057 | 15163 | **+16%** |
| 同节点 Pod→ClusterIP | 25247 | 33172 | **+31%** |
| 跨节点 Pod→ClusterIP | 12945 | 16713 | **+29%** |

这是全部数据里**未受控差异最少的一组**，第 1 节的头两条结论都来自它。但它并不免于漂移：
同一会话内锚点从 C 的 14959 变到 D 的 16584（+10.9%）。按锚点归一（即 §4.2 的比值口径，带着它的局限），
四格提升变为 +10.1% / +4.8% / +18.5% / +16.5%；跨节点 PodIP 的比值从 0.873 变到 0.914。
所以跨节点 PodIP 的 +16% 与锚点的移动同一量级，单凭这一格不能确立提升。

### 4.1 另一次独立测量

前一天还有一次同会话三形态的采集（A、B、D 各测一遍），可作为上表的复现验证：

| 场景 | A 纯 veth | B 串接·两项全关 | D 串接默认档 |
|---|---|---|---|
| hostNetwork 跨节点 | 16783 | 15440 | 15030 |
| 同节点 Pod→PodIP | 27871 | 25503 | 32355 |
| 跨节点 Pod→PodIP | 14421 | 13386 | 15801 |
| 同节点 Pod→ClusterIP | 27762 | 24961 | 32925 |
| 跨节点 Pod→ClusterIP | 13634 | 13174 | 17542 |

以 A 为基准：B 是 **−3.4% ~ −10.1%**，D 是 **+9.6% ~ +28.7%**。
与主表相比，A、D 的 Pod 侧绝对值最多相差 5.0%，hostNetwork 锚点最多相差 9.4%（D：15030 对 16584）；
但 **Pod 侧结论的方向与量级一致**。这次会话内锚点同样在动：以 A 为基准，B 为 −8.0%，D 为 −10.4%。

### 4.2 怎么读这两张表

**锚点不是恒定的，它只在一部分形态之间可比。** hostNetwork Pod 不经过任何 CNI 创建的 Pod 设备，
所以在 B、C、D、E 之间它应当相等，但观测值仍在 14959 ~ 16584 之间变动：**跨格锚点极差**为 1625，
是这四格中位数 15298 的 10.6%。这不是 §3 定义的离散（那是单格 n 次测量），而且它小于 §6.1 记录的
锚点单格离散（13% / 22%），所以这些数据分不清它是系统性漂移（采集时段、CPU 频率、邻居噪声）
还是各格自身的抽样噪声；无论哪种，都不是 CNI 造成的。它的两端 C 与 D 来自**同一会话**（+10.9%），
所以这种变动在会话内同样存在，不只发生在会话之间。

**但 A 与其余形态之间可能不适用**：安装 Cilium 会在宿主网卡上挂 tc/tcx 程序，而 hostNetwork 流量
**要经过宿主网卡**，所以 A 的锚点可能有真实原因与其余不同。这一点尚未确立：§4.1 中 A 的 16783
到 B 降为 15440（−8.0%）、到 D 降为 15030（−10.4%），但主表中 D 的锚点比 A 高 7.0%：
同一对 D/A 在两次会话之间相差 17 个百分点，详见 §5。

由此得到三条规则：

1. **同一会话只消除跨天差异，不消除漂移。** 即使在同一会话内，C→D 的锚点也移动了 +10.9%，
   所以同会话的绝对值同样带着漂移。从绝对值读出的差值，要大于**约 11%**（会话内锚点的最大移动
   10.9%；跨格锚点极差 10.6%）才能明确超出漂移，同会话与跨会话都一样。按这个标准，C→D 的
   +22% / +31% / +29% 成立，跨节点 PodIP 的 +16% 与锚点移动同一量级，§4.1 的 +9.6%~28.7%
   下端也达不到。§5 中 B 相对 A 的亏损逐格都低于这个标准，支撑它的是同一会话内四格方向一致。
   主表的 B 与 E 来自另外的会话，还要再叠加跨天差异。
2. **比值口径（Pod ÷ 同会话 hostNetwork）能消掉系统性漂移，但会放大采样噪声。** 分子分母
   各自的抽样误差会叠加，所以分母采样不足时它比绝对值更不稳。实例：默认档 D 的跨节点比值，
   §4.1 那次是 **1.051**（Pod 反超 hostNetwork），主表那次复测是 **0.914**；同一形态
   两次相差 14 个百分点。**这一条不宜作为结论引用。**
3. **跨越 A 与其余形态时，两种口径都不能直接用**，因为锚点本身可能被形态改变了。这时只能比
   Pod 侧的绝对值，并接受它带着漂移。

## 5. 串接本身的代价

串接意味着 Cilium 要在每个 Pod 的 veth 与宿主网卡上挂 tc/tcx 程序，每个包都要额外经过这些程序。
**把默认档的 `kubeProxyReplacement` 与 `bpf.hostLegacyRouting=false` 关掉之后，这部分开销是纯增量**：
BPF 的处理照常执行，而宿主协议栈的处理一步未省。

| 形态 | 相对 A（纯本插件）的 Pod 流量 |
|---|---|
| B 串接·两项全关 | **−3.4% ~ −10.1%** |
| D 串接默认档 | **+9.6% ~ +28.7%** |

（两个区间都取自 §4.1，那是唯一同时含 A 与 B 的会话。主表没有同会话的 B；与 B 只差
`kubeProxyReplacement` 的 C 在主表中相对 A 是 −3.8%~−7.9%。）

开启 host-routing 之后，这部分 BPF 开销由**追加**转为**替代**：宿主协议栈的对应工作不再执行，
代价被收回并转为净收益。

因此，**关掉这两项之后，串接等于用最多约 10% 的性能换取 NetworkPolicy 与 Hubble**
（没有哪一格单独越过 §4.2 约 11% 的门槛；这个亏损的依据是同一会话内四格同号）。
默认档不存在这个取舍，所以除非有别的理由，不要关闭这两项。

**hostNetwork 流量：只是观察，不是结论。** 有一次会话（§4.1）看到串接后 hostNetwork 变慢：
A 的 16783 对 B 的 15440（−8.0%）、对 D 的 15030（−10.4%）。主表结果相反：D 的锚点 16584 对 A 的
15493（+7.0%）。同一对 D/A 在一次会话里是 −10.4%、在另一次是 +7.0%，相差 17 个百分点，
所以这项开销并未确立。即便存在，host-routing 也无法补回：宿主网卡上的程序
对这类流量只有开销，而 host-routing 省去的是 Pod 到宿主协议栈之间的那一段，hostNetwork 流量不经过它。

## 6. delegated 模式（netkit）的增量低于测量分辨率

E 与 D 在四个 Pod 场景上的差值按 §4 行序分别是 **+3.7% / +0.5% / −3.8% / −7.5%**：方向并不一致，
且每一格都小于该场景自身重复测量的离散（同节点 4.9%~11.6%，跨节点 17.9%~19.7%；
各格 n 见 §4 表下注，哪一格对应哪个端点未记录）。
与此同时，锚点自身移动了 −8.6%，幅度超过其中任何一格。

**这是分辨率不足，不是差值为零。** 在这个量级上，跨会话对比不具备分辨能力。

### 6.1 netkit L3 与 netkit L2 的对比

两种 netkit 模式的比较只能用一种方式做：**同一会话内只改 `bpf.datapathMode`**，
中间重建 Pod，两侧都采 hostNetwork 锚点。该会话的日期与锚点的样本数未记录。

| 场景 | L3（`netkit`） | L2（`netkit-l2`） | 差值 | 档内极差 |
|---|---|---|---|---|
| **hostNetwork 跨节点**（锚点，n 未记录） | 15598 | 15787 | +1.2% | 13% / 22% |
| 同节点 Pod→PodIP（n=15） | 31531 | 31855 | +1.0% | 10.0% / 10.3% |
| 跨节点 Pod→PodIP（n=10） | 16255 | 16452 | +1.2% | 未记录 |

**三行都移动了同样的 +1%，包括锚点**，而锚点不受任何 CNI 配置影响。数据支持的唯一说法是：
L3 与 L2 在 Pod 侧的差别是会话噪声，凡记录了离散的格，差值都比离散小一个数量级。

理论上的方向是 L2 开销略高：它携带以太头、需要做邻居解析，L3 两样都不做。换算成单次事务耗时，
同节点是 L3 31.71 µs、L2 31.39 µs，差 0.32 µs 且方向与预期相反，这正是噪声的样子。

两档确实生效的旁证：Pod 网卡 MAC 在 L3 下是 `00:00:00:00:00:00`，L2 下是 `3e:b5:a2:c8:45:8f`。

## 7. netkit 省下的开销及其量级

netkit 设备的作用是**把 Pod 的 BPF 程序搬进设备的发送例程本身**：出节点的流量在发送方的
进程上下文里当场判定并直接转发到物理网卡，不再进入 per-CPU backlog 队列、不再切换到
softirq 上下文（内核提交 `netkit, bpf: Add bpf programmable net device`，v6.7）。
L3 模式还额外省去了 Pod 侧的以太头与邻居解析。

关键在于**它省掉的是哪一段**。上游把 netkit 的前置条件明确写成 eBPF host-routing
（`Documentation/operations/performance/tuning.rst`），两者是同一条路径上的前后两段：

- **eBPF host-routing** 绕开 iptables 与宿主上层协议栈，这是**主要部分**，即 §4 中的 +16%~31%；
- **netkit** 只负责把剩余的网络命名空间切换开销降为零。

默认档（D）已经开着 host-routing，所以 D→E 这一步在设计上只剩残值。把测量结果换算成单次事务
耗时可以看出它的量级：

| 场景 | D | E | 差值 | 占比 |
|---|---|---|---|---|
| 同节点 Pod→PodIP | 31.98 µs | 30.84 µs | 1.13 µs | 3.5% |
| 跨节点 Pod→PodIP | 65.95 µs | 65.63 µs | 0.32 µs | 0.5% |

一次 TCP_RR 事务跨 4 次命名空间边界（两端各进各出），所以同节点的 1.13 µs 摊到每次切换约为
**0.28 µs**，与「一次 backlog 入队 + 一次 softirq 唤醒」的量级吻合，说明差值的方向和大小都
合乎机制预期。但它只占同节点事务的 3.5%，而同一场景的重复离散为 4.9%（取自哪一格及其 n 未记录），
**低于分辨率**。

跨节点的情况更不利：同样的 1.13 µs 放进 66 µs 的事务里只有 1.7%，而该场景离散接近 20%（§6），
物理链路与网卡占掉了绝大部分时间。

**这项收益放大的条件是 CPU / softirq 接近饱和**（高 pps、多并发流），此时省下的每包开销会
转化成尾延迟与 CPU 余量。本测量是单流、1 字节、节点空载的延迟测试，这类收益在该形态下
无从体现。若业务负载会使节点的 softirq 处理饱和，应自行测量该模式；否则按 §1 选择形态。

## 8. 自己复测

```bash
# 1) 起 bench Pod：一对同节点、一对跨节点，外加一对 hostNetwork
#    工具容器需含 netperf；Service 里要同时暴露 12865 与 12866
# 2) 每档跑：
for i in $(seq 10); do
  kubectl exec bench-cli -- netperf -H <目标IP> -p 12865 -t TCP_RR -l 10 -- -r 1,1 -P ,12866 \
    | awk 'NR==7{print $6}'
done
```

注意事项：

- **要对比的形态排进同一个会话**，不要跨天比较。
- **锚点每档必采**，否则无法判断差值是不是漂移。
- **要分辨 5% 以内的差值，3 次不够。** 按本环境的离散水平，同节点场景约需 n ≥ 20。
- **切换形态后要重建 Pod。** 设备类型在 Pod 创建时确定，存量 Pod 不会跟着变。
